## A. The user flow: pages, steps, screens the user sees

### User flow inventory: findings (read from code, nothing run)

Rows: `flow.json`, 138 rows (flow-001 to flow-138). References are file:line in /Users/Shared/Projects/camera.

#### Pages and order as the code builds them
1. Stored pages (`events.customPages`, sorted by `order`) come from the event. Events are created with an empty list.
2. At read time (`GET /api/events/[id]?audience=guest`, route.ts:205-213) two defaults are added, never stored:
   - default consent page (3 required checkboxes with links) right after the leading welcome page(s), only when the event gets the journey defaults (event flag or global switch) and has no own consent page before the photo (default-pages.ts:59-73);
   - default login page after welcome and consent, when photo vetting is on (every new event) and there is no own login page before the photo (identity-page.ts:83-94).
3. No welcome page is ever added by default; it exists only if an editor adds '+ Welcome (step 0)'.
4. The capture page splits the list at the take-photo page: before it = onboarding, after it = thank-you pages. No take-photo page stored = everything is onboarding (page.tsx:174-199).
5. Onboarding renders welcome, accept, who-are-you, cta, restart by type (page.tsx:1203-1323); other types are skipped.
6. Built-in steps (not pages): frame picker (only with more than one frame) > camera (touch device: the phone's own camera app; desktop: live webcam with shutter) > one photo screen (ReframeStep: Retake, Reset, Continue saves) > saving overlay > vetted: waiting card / not vetted: share card (or a 'Saved' card when share is off) > NEXT.
7. After NEXT: thank-you pages if any, else straight back to the camera. After the last thank-you page the code restarts at the first onboarding page and clears consents and user info (page.tsx:1084-1093), which contradicts the camera-again behaviour above and in docs/WELCOME_STEP.md.
8. Levels: pages and every page text exist at event level only. No partner or global page template. Global = dictionary in code (messages.en.ts, 228 keys, + messages.hu.ts) and one switch (Settings > Journey defaults). Partner = default brand colours, logo/frame/image libraries. uiLanguage is event only (partner level #353 not built).

#### Top problems
A. Language gaps (flow-011, 012, 024-026, 054, 064, 066): the page editor creates accept, cta, restart and welcome pages with English text stored (Please accept, Next, Next step, Ready for the next guest?, Start again, Start). Those pages pass raw config text to the components, no dictionary key exists, so a Hungarian event shows English. Only the injected consent/login pages and the take-photo texts translate (textOr trick: a stored text equal to the English default counts as unset).
B. Defaults you cannot see or edit: the injected consent and login pages have no editor entry (flow-002, 003); the dictionary has no admin screen (flow-079); the take-photo editor pre-fills and saves English defaults as own text (flow-006), so default and own cannot be told apart. Only the approval and redirect texts use the grey-placeholder pattern.
C. Duplicated settings and keys: login texts exist twice per field (login.nameLabel vs nameLabelEditor, sso, form, placeholders: flow-044 to 051); share.suggested vs flow.shareSuggested (flow-118); camera.prompt.desktop vs .device (flow-089, 090); consent privacy link vs email.termsUrl vs notifications.termsUrl (flow-032); restartButtonText vs buttonText (flow-066); consent list vs single checkboxText (flow-033, 034); three logo mechanisms: scenario logos, events.logoUrl+showLogo, partner/theme logo (flow-068, 082, 137), and the event editor's help text says the event logo shows during loading, which the code does not do.
D. Settings that do nothing or are ignored: showFrameOnCapture has no reader (flow-097); the editor's Prompt Description never reaches phones (SystemCameraCapture gets no description, flow-090); Back buttons on four pages are never wired (flow-067); captureButtonText/retryButtonText kept but unused (flow-100); the page editor has no active/inactive control, so a page cannot be switched off (flow-009).
E. Colour leaks: the Start button and the CTA picture buttons default to blue #3B82F6 / white and ignore the theme (flow-018, 062); the desktop shutter, ring and prompt gradient use brandColor or the same blue, not the theme order welcome > event > messmass > default (flow-093, 094); waiting/share backdrop is a hardcoded black 55% scrim (flow-114). Page, text, card colours and font come from messmass only, no camera-side override (flow-071 to 073).
F. Hardcoded or technical text reaching users: Facebook/Twitter/LinkedIn/WhatsApp buttons and share URLs (flow-119); 'Google'/'Facebook' labels, the ↗ and 🔗 glyphs; flow.email.* texts mention RESEND API key and sender domain (flow-107); 'Job ID' in the try-on box (flow-121); raw SSO error text from the URL (flow-123); 'Loading...' with an emoji in app/capture/loading.tsx, English and unthemed (flow-135); the word 'guest' in defaults (flow-136); PWA icon is a fixed camera icon (flow-126).
G. Empty text cannot fall back to a default on stored pages: the API requires title and buttonText for every page except take-photo (route.ts:475-477), so plan item 36 (empty = default) works only for login description/labels and take-photo texts (flow-024, 039).
H. Data risk (from code, not run): a CTA page with no URL and a Continue button records a consent with an empty checkboxText, which POST /api/submissions rejects (flow-056).
I. Old /capture vs the event page (flow-129 to 135): no theme, language, consent, login, vetting, reframe screen or tour; browser alert() messages; own hardcoded English strings and share caption; FileUpload used only there; photos always shown on the wall without a consent step (owner-approved, plan item 94).

#### Not built yet (planned, no code)
Welcome page screen generated from the default slideshow, sample selfie fallback, frame/message toggle, frame toggles and positions, partner default language, Dictionary admin screen (flow-005, 127, 128).

## B. Texts and e-mails

### Texts: findings (read-only research of /Users/Shared/Projects/camera, 72 rows in texts.json, all 228 dictionary keys covered)

#### Levels today
- Global = the dictionary in code (lib/i18n/messages.en.ts / .hu.ts). No admin screen edits it (the planned Dictionary item, plan item 19, is not built). Changing a default = a code change.
- Partner = nothing. The Partner type holds no text or language (lib/db/schemas.ts:135-178) and event creation copies only colours, frames, logos from the partner (lib/db/events.ts:166-206). #353 (partner default language) is not built.
- Event = the only editable level: Event fields, stored pages (customPages[].config), sharePage.texts, notifications.*, frameDesign.messages, slideshow.screenDesign.texts.

#### How a text is resolved today (the real rule)
1. Dictionary-only text: translate(event language, key); language = Event.uiLanguage, English when missing (lib/i18n/index.ts:31). The new-event form and POST /api/events cannot set it (events/route.ts:147); provisioned events start English.
2. Editable page text, rule `own(key, stored)` = textOr (index.ts:42-48): stored non-empty text wins, except in hu a stored text exactly equal to the English default of that key counts as not set; an empty stored text gives the dictionary text (so the editor can never blank it). English events: stored always wins. Used for: all take-photo settings (page.tsx:320-343), login page (WhoAreYouPage.tsx:73-79), CTA visit button and redirecting text, loading text, approval texts (page-texts.ts), public photo page texts (share-page-settings.ts:35-45).
3. Pages with NO dictionary fallback, shown as stored: consent (AcceptPage.tsx:99,177), CTA title/description/Continue, restart, welcome. The API requires title and buttonText on every page except take-photo (events/[eventId]/route.ts:475-477). A hu event shows whatever English the editor saved.
4. Default consent and login pages are built at read time in the event language (default-pages.ts, identity-page.ts), only if the event has the journey defaults / needs vetting and has no own page of that type; they are not in the page editor.
5. E-mails: normalizeSubmissionEmailPolicy(notifications, language) -> emailTemplateIn: a stored template exactly equal to one of the 4 English defaults is sent as the same default in the language; anything else as written; empty -> emailDefaults(language) at send time (submission-notification.ts:136-151). Terms link: stored English default URL -> language URL, other URLs as written. Sender name 'The Selfie' is never translated. 'Not approved' e-mail is fixed; the 'photo approved' e-mail reuses the after-save template.
6. Event editor and new-event form pre-fill English defaults and the API stores them (edit/page.tsx:190-211,531-569; events/[eventId]/route.ts:43-66 stores sender name and terms URL even when blank). Everything the heuristics in 2 and 5 do is to undo this freezing.

## C. Graphics, screens, colours, fonts, links

### Graphics, screens, colours, fonts, links: findings (read from code, camera main, 2026-10-09)
Rows are in graphics.json (108, ids gfx-001 to gfx-108). levels_today: "event" = only the event can set it; "none" = code constant or messmass.

#### 1. The visual channels and the real rule today
- Frame: an event with an ACTIVE assignment of a complete frame uses its own frame(s) (picker, 1 = auto); otherwise the generated frame (frameDesign.variants) if images exist; else none. Each generated image is drawn on the frame its message chose (library frame with a message area), else the old base picture, else the generated layout. A random variant per shutter press. [001-005, 010-013]
- Global -> Partner -> Event exists in code only for frames and logos, and as a COPY: Partner.defaultFrames/defaultLogos are copied into a new event and cascaded while framesOverridden/logosOverridden is false. Images, colours, fonts, slideshows, messages, welcome page, e-mail footer have no partner or global default. [003, 004, 027, 098]
- Logo on journey pages: Event.logos[onboarding-thankyou] (first active by order) -> theme logo (messmass partner/home team logo from the snapshot) -> event emoji -> nothing. Loading screens use only Event.logos[loading-*], no fallback. Share page and e-mail: theme logo -> emoji (-> product name). [023-031, 066, 093]
- Colours: page, text, card, link = messmass style snapshot (event > partner > template > system default), contrast-repaired. Buttons = welcome Start-button colours > Event.brandColor/brandBorderColor (own, or copied from the partner) > messmass > default. The generated frame uses the raw messmass colours, not the repaired ones. [043, 051-057, 008]
- Fonts: messmass style font. Pages load any Google font or the custom messmass file; the frame draws only Inter/Roboto/Poppins/Montserrat or a custom file, else Inter; e-mail only names the family; a screen design may override with a Google font name. [014, 060, 074]
- Picture fields (4 welcome pictures, CTA picture, e-mail footer, screen overlay): one plain URL string per event, no inheritance, no default; the Images library is only a chooser/copy of the URL. [035-040, 045, 067, 070, 095]
- Slideshow: event-level only, from code defaults (indigo gradient, 5 s / 1 s / buffer 10, 16:9). No default slideshow is created for any event. [068-081]
- Links: every tracked/short link ends on /capture/<event>; the slideshow QR is a typed URL; the welcome-screen QR is baked pixels. [072, 085, 040]

#### 4. What is needed so the welcome-page screen picture and the slideshow stage come from the same parts
- Today they share nothing: the stage is live DOM (gradient, photo window, overlay, QR SVG, texts, event font; SlideshowPlayerCore + ScreenDesignLayers), the welcome picture is a hand-made JPEG pasted into customPages[welcome].screenImageUrl. [040, 070-075]

[079, 035, 073]

## D. Admin editors and screens

### Admin editors and screens: findings (camera, read from code; rows ed-001..ed-068 in editors.json)

#### 1. The real structure today
- The menu has 17 items in 6 sections (lib/adminNavigation.ts). A partner user sees 3 of them: Dashboard, Events, Partners. 50 of the 68 rows in editors.json are reachable only by a link (or not at all).
- The real structure is four hubs of cards (Dashboard, Event overview, Partner overview, Operations hub) with the editors hanging below them. The event tab bar has 4 tabs (Overview, Vetting, Queue, Analytics); the 7 event editors (edit, frames, logos, images, slideshows, landing pages, layouts) are not tabs. The partner level has no tab bar.
- Queue and Analytics tabs are shown to partner users but render global-admin pages that redirect them to /admin; the dashboard vetting/queue tiles do the same (ed-002, ed-007, ed-016).
- The "Libraries" section mixes 4 real libraries (frames, logos, images, generated-frame rollout), 2 try-on config lists (Garments, AI Setups) and 3 read-only cross-event inventories (Landing Pages, Slideshows, Global Galleries) that create nothing and only link into event editors.
- Page eyebrows (Apps, Camera Core, Resource Inventory) are not menu section names; sidebar highlight is by path prefix, so Operations lights up on Garments/AI Setups.
- Size signal: Edit event 1192 lines and 9 setting groups on one form; Event pages editor 1095; try-on moderation table 1722; slideshow + layout + landing editors about 2900 together.
- Defects found on the way: partner StyleSections "Manage logo assignments" links to /edit#logos (no such section); delete-event button shown to managers but the API needs partner admin; landing page logo upload needs global admin but the editor is open to managers; the try-on setup list on Edit event is empty for managers (global-admin API); server-rendered slideshow, layout and landing editors have no event-scoped access check on render (APIs check on save).

#### 2. Same data edited in several places
- Brand colours: events.brandColor (Edit event), welcome and CTA button colours (Event pages editor, wins over it), partners.defaultBrandColors (Edit partner), plus the messmass style.
- Logos: events.logoUrl + showLogo (Edit event), events.logos[] by scenario (Event logos), partners.defaultLogos (Partner logos), landing_pages.logoId (global library only), partners.logoUrl (no editor at all).
- Pictures: one ImagePicker used 7 times, all event level, plus two own upload paths (slideshow background, landing QR) and three Images library pages.
- Terms and consent: notifications.termsUrl (Edit event), accept-page checkboxes (Event pages), landing page terms/privacy markdown, and a default consent page that is code only.
- Waiting-for-approval words: sharePage.texts + pendingTryOnMessage (Edit event) and take-photo pending* texts (Event pages); email subjects and bodies a third group.
- Vetting: photoVetting.required (Vetting tab, global admin only) vs tryOn.vettingEnabled (Edit event) vs the hidden /admin/photo-vetting rollout; one event's vetting has two URLs with different rules.
- Short links: events.shortUrlSlug (Edit event) vs the tracked-links panel on the overview. Setup choice: event setting, ?cameraId mode, and setup.defaultForGarmentTypes.
- frames.messageArea in 3 screens (global edit, partner card, event card); only global admins can rename or describe an item, partner and event uploads cannot be renamed.
- events/new is a copy of the Edit event form (850 vs 1192 lines) and has drifted (no language, tour, colours, footer picture, share texts).
- Slideshows and landing pages: embedded cards on the overview AND global inventories, same documents. User roles: SSO role on Users, partner role on Partner overview.

#### 3. Event-only, partner-only, global-only
- Only colours, frames and logos are inherited event from partner (inheritPartnerDefaults). Everything else is typed per event: language, loading text, 3 emails, share-page texts, journey pages (welcome, consent, login, CTA, photo texts), try-on settings, slideshows, layouts, landing pages, short links.
- Partner has no pages, texts, emails, pictures, try-on or slideshow defaults; Global has no default-content editor (journey defaults are code in lib/events/default-pages.ts plus one switch).
- Users get a default consent page and login page that the Event pages editor never shows (it reads stored pages); pages cannot be switched off, only deleted.
- Global-only with no partner level: garments and AI setups (events pick straight from global, breaking the one-way Global -> Partner -> Event rule of docs/LIBRARIES.md).
- Partner-only: user access, delete partner, messmass logo import. Partner managers cannot edit the partner's default colours but can edit its frame and logo defaults.
- Orphans (no screen): HashtagInput, RemoveSubmissionButton, email-preview, partner toggle, submission archive/restore, frames.hashtags.

#### 4. Repeating patterns that could be one component
- Library page: 7 files each with their own call(), errorText(), GRID and the same three sections (In library / Available / Upload). One LibraryPage(level, kind) with per-kind options (frame defaults, logo scenarios, message area).
- List + form: frames, logos, garments, setups, partners, events, each with a new and an edit copy (setups and events new/edit repeat the form).

## E. Data model: where each value lives and how it is resolved

### Model findings: inheritance today (Global -> Partner -> Event)

Read-only code read of camera main. 91 rows in model.json; every claim there carries file:line. "unknown" is stated where the code did not say.

#### 1. Mechanisms that exist
1. Copy at creation. inheritPartnerDefaults (lib/db/events.ts:166) copies Partner.defaultBrandColors / defaultFrames / defaultLogos into the new event. Three creation paths use it: POST /api/events, messmass provisioning, savetheworld provisioning. Flags start false. User pages read only the event's copy; the partner value is never read at user time.
2. Cascade. updateChildEventsFromPartner (events.ts:72) runs on partner PATCH (whenever the key is in the body) and on library PUT (only when defaults changed). For events with the flag falsy it overwrites brandColor/brandBorderColor (with null when the partner clears) and REPLACES the whole frames[] and logos[] arrays (rows rebuilt, addedAt/addedBy lost, an empty list included).
3. Three override flags on Event. brandColorsOverridden is semantic (true while the event keeps a colour of its own, false again when both are cleared: brand-colours.ts:43). framesOverridden / logosOverridden are set true by ANY touch of the list (assign, remove, toggle, reorder, upload) and silently by keepInEvents when the partner removes a library item; only reset-style sets them false. Nothing in the user path reads a flag; only the cascade and the admin indicators do.
4. Reset (resetEventStyleToDefault, events.ts:253): flag false AND the event's colours/list replaced by the partner's current default, or by [] / null when the partner has none.
5. frameDesign.messagesOverridden: recomputes itself (true only while the list differs from DEFAULT_FRAME_MESSAGES). The one code-level global default that is re-applied to stored events (at snapshot refresh).
6. Read-time defaults, nothing stored: default consent and login pages (withDefaultJourneyPages), gated by Event.journeyDefaults OR admin_settings defaults-rollout (consent) and photoVetting.required (login). Missing = default for photoVetting, tourEnabled, uiLanguage, showLogo, sharePage/visualSettings (normalize*), library scope (missing = global).
7. Text resolver textOr / own (lib/i18n): event text ?? dictionary of event.uiLanguage. A stored text equal to the English default counts as not set in other languages (heuristic, because editors saved defaults as their own).
8. Theme resolver resolveEventTheme (event-theme.ts:113): button fill = welcome-page Start button > event brand colour (own OR a partner copy) > messmass style > system default, reported as buttonSource. Page/card/text/link/radius/font/logo come only from the messmass snapshot or the system default; no event or partner override exists.
9. Library rules (rules.ts): an OFFER filter (Global library -> Partner library -> Event), not a value resolver. A partner's first library save freezes the computed list of all three kinds.
10. Other resolvers: try-on setup (request > garment default > event.tryOn.setupId > camera preference > global default > legacy, records setupSource); slideshow stageAspect null -> constant 16/9; event tryOn policy beats Slideshow.submissionSourceMode (parent beats child).

#### 2. How they differ
- Colours, frames, logos are WRITE-TIME inheritance (copy + flag + cascade). Texts, default pages and switches are READ-TIME defaults. Two opposite models; only the first has a partner level.
- "Global" is code for texts/colours/messages (dictionaries, tokens, DEFAULT_FRAME_MESSAGES, photo-vetting constant) and data only for libraries and two admin_settings docs (defaults-rollout gates one thing; card-display is an admin UI preference). A global admin cannot edit a default text.
- Only the try-on resolver and ButtonColourSource show which level won. EventTheme.source and buttonSource can disagree (source says 'messmass' whenever a snapshot exists).

#### 3. Fields that follow no pattern
- No partner value at all: uiLanguage (planned #353, not built), tourEnabled, loadingText, photoVetting, tryOn.*, notifications.* (templates, sender name, termsUrl), sharePage.* (flags, pendingTryOnMessage, ten texts), visualSettings.buttonSize, emailFooterImageUrl, Event.logoUrl/showLogo, every customPages text/picture/colour, slideshow/layout/landing page/short link fields, shortUrlSlug.
- Default frozen into the event: edit forms and normalize* save English defaults (loadingText, pendingTryOnMessage, sender name, terms URL, new-page literals 'Next', 'Start', 'Start again'); scripts backfilled email defaults into events. Accept/CTA/restart/welcome title and buttonText are required on save, so they cannot be left empty to follow a default.
- Five-plus logo channels: Event.logoUrl+showLogo, Event.logos[] (4 scenarios, one has no consumer), theme logo (messmass partner or home team), Partner.logoUrl (set once, only if missing; read only without a snapshot), emoji, LandingPage.logoUrl (frozen copy), imported partner logo.
- Dead or unread: Partner.defaultBrandColors.accent, Partner.isActive (no effect on events), Partner.eventCount/frameCount, customPages showFrameOnCapture/captureButtonText/retryButtonText (no user reader found), Event.partnerName (stale cache, never updated).
- Naming differs across levels: partner primary/secondary = event brandColor/brandBorderColor.
- Creation paths write different field sets: POST stores sharePage, visualSettings, notifications, tryOn flags; messmass provisioning stores none of them (emails off); savetheworld does not set journeyDefaults.

#### 4. What comes from messmass, and when
- Provisioning (POST /api/internal/messmass/partners|events): partner name (create only), logoUrl (only if missing), ids; event name/date copied once, idempotent. No later name sync.
- Frame-context snapshot (Event.frameDesign.context): event name/date, teams + logos, partner-or-home-team name/logo, template, style (font, heading, hero, page/card/button/link colours, radius). Taken at provisioning, on admin Refresh, on messmass push (theme-updated: marks stale, refreshes 12 events / 40 s), and by a user visit when stale or older than 24 h (retry gap 10 min). A failed fetch keeps the old snapshot. Lag up to 24 h.
- Outbound only: camera-native partner name/logo, tracked-link totals. Partners with source 'messmass' are never pushed back.

#### 5. What one resolver ("event ?? partner ?? global ?? built-in, source shown") must replace or wrap
Replace or wrap: resolveEventTheme + loadEventTheme, textOr / own / sharePageText / pendingTryOnText / emailTemplateIn / redirectingText / approvalTexts, normalizeEventSharePageSettings / normalizeSubmissionEmailPolicy / normalizeEventButtonSize / normalizeUiLanguage / photoVettingRequired, eventGetsDefaults + withDefaultJourneyPages, captureFrameOf and the logo picks (shownLogo, CaptureStageShell, the capture page), the tryOn setup resolver, stage aspect. Keep: library rules (offer filter), messmass snapshot (it is the "messmass" tier between partner and built-in), cascade only if copies are kept.
Needs a new column or null-means-follow: no partner storage exists for any field except colours/frames/logos; the global tier is code, so a DB global tier means moving dictionaries/constants behind a read, or a layer that sits above them.
Risks:
- Cascade replaces whole lists (events.ts:120-143) and Reset replaces with partner list or []: both remove event assignments, against "nothing set is ever deleted". Read-time resolution (no copy while following) would remove the need.
- framesOverridden / logosOverridden never reset by themselves (only brandColorsOverridden and messagesOverridden recompute). Any toggle freezes the whole list for good; the user path ignores the flags. A resolver needs per-field "own value present" (null = follow), not per-list flags.
- A copied partner value is stored like an own value (brandColor); only the flag tells them apart and flag undefined on old events is unverified. Migration must infer "follows" without deleting values.
- Stored defaults (English text, 'The Selfie', default terms link, button size 'md') look like own values; textOr's equal-to-English heuristic cannot distinguish a deliberate identical text.
- Precedence inversions: welcome-page colours beat the event colour; event tryOn policy beats the slideshow. Decide each deliberately.
- Stale caches to retire or label: Event.partnerName, Slideshow/Landing eventName copies, 24 h snapshot lag, LandingPage and email-footer picture URL copies.

## F. How the admin screens use the design system (register item 152)

### GDS use in the camera admin: findings (measured 2026-10-09, main 6db8dcd, GDS 6.3.0)
Scope: 128 files (57 app/admin, 56 components/admin, 15 components/gds; 53 are page.tsx), 26,598 lines. Every number, per file, is in gds.json. Read-only scan, cross-checked with grep. Nothing was run in a browser or on a phone.

#### Overall picture
- The owner's fear is confirmed, and it is worse than "hard-coded": 835 `style={{` objects in 79 files, 855 px/rem/em literals, 831 raw div/span/p/label/input/h1-h4 tags (plus 230 other raw tags). Inline styles in app/admin + components/admin grew 620 -> 792 (+28%) in the 8 days since gds_fix_handover.md, mostly in the new library screens (+19 partners/logos, +16 partners/images, +16 events/frames) and GeneratedFramePanel (+39), which copied the same pattern.
- Tokens are almost not used, and the ones that are used do not exist. 220 `var(--gds-...)` references in admin code; 213 (97%) name tokens no GDS version defines: `--gds-color-muted` 107, `--gds-color-border` 85, surface 13, shadow 3, accent/danger/space-2 5. Checked in gds-theme styles.css and dist, gds-core and gds-admin dist, app/globals.css. An undefined var makes the whole declaration invalid, so `border: 1px solid var(--gds-color-border)` draws no border, "muted" text is not dimmed, `--gds-color-surface` is transparent. By CSS rules, not yet confirmed in a browser; it is the likely cause of the "messy, unfinished" look (cards without edges).
- The 7 valid references sit in the two hand-rolled modals. Zero uses of any `--gds-space/radius/font-size/weight/elevation` token. Using them would not work either: camera runs the plain `gdsTheme`, which emits only colour roles, overlay, motion, safe-area at `:root`; axis tokens exist only in preset/brand lanes (gds#765, `gdsTheme = baseTheme`, no cssVariablesResolver). In this lane the real scale is `--mantine-*` (63 uses) and component props (Mantine spacing/radius props with a token such as `gap="md"`: 163 uses, numeric ones: 29).
- Values drift: 18 distinct border-radius, 24 gap, 30 padding values; 36% of spacing and 55% of radius literals are not on the GDS scale (0.5rem 84x, 1.5rem 71x, 0.35rem 51x, radius 0.875rem 14x, font 0.8125rem 14x). 57 raw `--mantine-color-<palette>` colours, 133 `dimmed` greys (#868e96) where `--gds-text-meta` exists.
