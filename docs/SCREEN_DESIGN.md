# Giant-screen design (slideshow screen design)

A slideshow can carry a **screen design** (camera#309): a picture drawn over the stage with a transparent window where the photos play, a QR code
made by camera, and a few short texts. It is how a club's giant-screen layout (the stadium LED wall of MTK x Vasas) is shown without anyone
laying it out by hand. Stored as `Slideshow.screenDesign`, edited in the slideshow editor ("Screen design"), checked by
`lib/slideshow/screen-design.ts` (`parseScreenDesign`) on save, sent to the player with the playlist settings.

## What it is made of

All positions are percentages of the stage (a 16:9 stage, like the designers' 1920×1080 picture), so the screen looks the same at any size:
the player makes the stage a size container and the sizes are `cqh`/`%` units.

| Part | Field | Notes |
|---|---|---|
| Overlay picture | `overlayImageUrl` | A 1920×1080 PNG drawn over the whole stage, transparent where the photos play. https only. Chosen with the picture picker from the partner library or uploaded into the event Images library (PNG, WebP or SVG: a JPEG cannot be transparent), or pasted; stored as the plain address (docs/LIBRARIES.md). |
| Photo window | `window {left, top, width, height}` | Where the photos play. The photos are cropped to it (`photoFit: cover`) or shown whole (`contain`). The overlay's own rounded corners and border cover the edge of the photos. |
| QR code | `qr {url, x, y, size, color}` | `url` is where it points (https, up to 300 characters), `x`/`y` its top left corner, `size` its side as % of the stage **width**. The server draws it as an SVG of its dark modules (level M correction), by default white, so it is light on the dark overlay like the designers' example (a QR reader that reads inverted codes scans it; a phone camera does). |
| Texts | `texts[] {text, x, y, width, size, align, color}` | Single line, up to 8, each at most 120 characters; `size` is % of the stage height; white with a soft shadow by default. |
| Font | `fontFamily` (optional) | The texts are written in the event's own font, from its messmass report style (a Google font, or the style's custom font file), loaded by the player. A `fontFamily` set on the design replaces it with a Google font; leave it out. |

## Failover background image

`Slideshow.backgroundImageUrl` is the picture behind the gradient and slide photos when the playlist is empty or letterboxed. The slideshow editor uses the event Images picker: the manager can choose an image already in the partner library or upload it into the event Images library, even before creating the slideshow. The slideshow stores the selected URL and can be cleared to return to the gradient. It is not a partner default; each event's slideshow makes its own choice.

## The default screen of every event (camera#326, camera#327; step 7 of docs/BUILDING_BRICKS.md section 8)

Every event gets a **default slideshow** with a ready-made screen design, so no event starts with an empty stage and nobody has to lay one out. It is what the welcome page screen
and the giant screen start from; an editor changes it, or makes another slideshow and sets that as the default.

- **Layout:** the MTK x Vasas measures above are the default layout (`DEFAULT_STAGE` in `lib/screen/default-stage.ts`): photo window, the QR code centred alone in its panel, and a **band under the
  window with one big line, the written address** (owner, 2026-10-09: one line, as wide as the window, scaled to fill that width; the earlier two-line band of camera#487 with the call to action above the address is gone). One layout, in percent of the 16:9 stage, used by the live stage and by the picture of the welcome page.
- **Picture:** drawn by the server (`renderDefaultOverlay`, `@napi-rs/canvas`) in the event's own colours (its page colour and its button colour, from the messmass style): a night-stadium
  background (gradient, floodlight glows, a faint pitch circle and half-way line), panels for the QR code and the texts, an accent border round the window, and a transparent window.
  The same colours give the same picture. Stored in Vercel Blob under `screens/<event uuid>/default-<hash>.png`.
- **QR code and address:** the event's tracked **"Giant screen"** link (placement "Giant screen", kind QR, `lib/short-links/store.ts`) is made if the event has none, and reused if it has one, so
  the scans are counted on their own and reach messmass like every tracked link. The QR points at `https://go.messmass.com/<link slug>`. **The address written under the window is the event's own short address
  whenever it has one** (`Event.shortUrlSlug`, e.g. `go.messmass.com/mtk-vasas`), else the tracked link's (`go.messmass.com/<link slug>`), without the protocol (`writtenAddress` in
  `lib/slideshow/default-slideshow.ts`; owner, 2026-10-09: the written address is never the link's random code when the event has an address of its own). Both addresses reach the capture page and both are counted; only the QR's scans are counted as "Giant screen". What an editor types in a text is kept as typed.
- **A text that fills its box (`fit`, owner, 2026-10-09):** a screen design text can be one line scaled so that it fills the width of its box (`ScreenDesignText.fit`); `size` is then not used: the line takes the size that fills the box exactly (at most 30 % of the stage height, the largest size a text can have), so a long one never wraps and a short one grows to the box width. A first version capped the line at its stored size, and a short address stayed at 80 % of the box (owner, 2026-10-09: "it is not scaled"). The default band is drawn for a nominal line of 12 % of the stage height.
  The live stage measures the line at a reference size and scales it by box over line (again when the font arrives or the box changes, `components/slideshow/ScreenDesignLayers.tsx`); the server picture of the welcome page does the same with the canvas measure; both use `fitSize` (`lib/slideshow/screen-design.ts`).
  The default address text is `fit`, with a box as wide as the photo window. In the slideshow editor a text typed into an empty row is put under the window, as wide as the window, with **Fill the box** ticked (the Size field is then greyed out); a text without it keeps its fixed size. A QR code address typed without `https://` gets it when the design is saved; a refused save names the part that is wrong (the address, or the place and size) and is logged (`slideshow.save_refused`).
- **A stadium background of the library (issue 326, item 1; docs/LIBRARIES.md, "Stadium backgrounds"):** when the event has one to use (its own, its partner's, else a random global one, picked once and stored on the event as `Event.stageBackground`), the stage is drawn on it: the picture fills the stage, the event's page colour lies over it (62 %), the floodlights glow in the accent colour, then the same panels and photo window (`renderStageOverlay`). **With none in the library the stage is exactly the one drawn by code**, so an event that chooses nothing is unchanged. An existing event keeps its stage until an editor presses **Draw the stage again** in the card **Default stage** (Slideshows page); see "The stage on a stadium background" below.
- **No call to action line by default:** the earlier default had a call to action picked at random from the dictionary (`screen.qrText.1` to `4`) above the address; it is not part of the default any more. The wordings stay in the Dictionary, and a designed screen
  (like the MTK x Vasas one) keeps its own call to action next to its QR code.
  **Existing default slideshows keep the layout they were made with**: only a new event, or a default slideshow made again, gets this layout (an editor can also move the texts of a design by hand).
- **A QR text of the library (issue 326, plan items 4, 9, 10 and 49; `lib/library/qr-texts.ts`):** Blocks > **Global Dictionary** > **QR texts** (`/admin/dictionary`, global admins; `GET`, `POST /api/qr-texts`, `PATCH`, `DELETE /api/qr-texts/<id>`; collection `qr_texts`) holds short lines ("Scan & smile") in any locale from the canonical `UI_LANGUAGES` registry, at most 40 characters, and an active flag. The editor displays locale names in their native form with the English name in parentheses. When an event's default slideshow is made, **one active exact-language text is preferred, then an active English text; a selected line is picked at random, once, and stored on the event** (`Event.qrText = { qrTextId, pickedAt }`), and put in the slideshow as a second text, **above the QR code in the panel of the right column**, as wide as the QR code and scaled to fill that width (`DEFAULT_STAGE.qrText`; the written address stays the first text). **With no matching QR text in the library the slideshow is exactly what it was** (one line, the written address), so an event that chooses nothing is unchanged; the Dictionary's `screen.qrText.1` to `4` are not used by the default. After it is made the line is a text of the slideshow like any other: the editor changes or removes it in the slideshow editor, and that is the event's own, which always wins; the library is never read for that event's slideshow again (switching a text off or deleting it changes no existing slideshow). An existing default slideshow gets a line only by being made again.
- **When it is made:** for every **new** event, after the response (the admin form, messmass provisioning, savetheworld provisioning); on demand with **Create the default slideshow** on the
  event's slideshows list when it has none (`POST /api/admin/events/<id>/default-slideshow`). Making it twice changes nothing. **Existing events get nothing automatically**; the backfill is the card **Welcome page screens for existing events** on the Slideshows page (a dry run that only counts and lists, the events chosen one by one, a confirmation in the page before anything is written; the owner's go decides when it runs; see "Existing events" below).
- **The default flag:** `Slideshow.isDefault`, at most one per event. **Make default** on any slideshow's card sets it (`PUT` of the same route; the new one is flagged before the old flag is
  taken off, so an event is never without one). The default slideshow cannot be deleted: make another the default first.
- **Built since this list was written:** the sample selfie in the photo window (issue 540, below), the stored picture of the welcome page screen drawn from this layout (step 8, the next section). The text levels for the call to action (step 6) no longer matter for the default: it has no call-to-action line (see above); a slideshow that has one keeps its own text.

## The welcome page screen picture (issue 327; step 8a of docs/BUILDING_BRICKS.md section 8)

The welcome page shows the giant screen as a picture above the Start button. For an event with a default slideshow that picture is **drawn on the server from the default slideshow**, the way
the stage draws it live, so the welcome page and the stage show one design (`lib/screen/welcome-screen.ts`, `lib/screen/welcome-screen-store.ts`).

- **What is drawn, back to front** (the player's own order): what is in the photo window, the overlay picture with its transparent window, the QR code (its dark modules, from the same `qrcode` library) and
  the texts (bold, one line, soft shadow, the event's font through `lib/frame/fonts.ts`). The window shows the event's frame over a stand-in (a head and shoulders in the event's colours) until the
  library has sample selfies (step 5); a real photo is not used: the picture is a stored image, not a live view.
- **Stored on the event** as `Event.welcomeScreen` `{ url, key, generatedAt, renderVersion }`, under `screens/<event uuid>/welcome-<key>.png` in Vercel Blob. The `key` is the hash of everything it is drawn
  from (the design, the colours, the font, the frame, the drawing version), so asking again costs nothing and a change in any of them draws it again. **It lives next to the pages, never in them: a page's own
  `screenImageUrl` is never touched and always wins when the page is shown.**
- **When it is drawn:** for a new event, right after its default slideshow is made (after the response; `lib/screen/new-event-screen.ts`); on request with **Draw the welcome page screen** on the event's slideshows list
  (`POST /api/admin/events/<id>/welcome-screen`, which also makes the default slideshow when there is none: this is how an existing event gets one, by an admin's choice); and **every time the
  default slideshow is saved with a screen design or made the default (Make default)**, also for an event that had no picture yet (owner, 2026-10-09: "the welcome composition with the big screen has to use exactly the one created for
  the slideshow, so whenever a slideshow is updated, it has to be updated as well"; an earlier rule only redrew a picture that already existed). So the picture is always the default slideshow's own screen: its overlay, QR code and texts (a `fit` text is scaled to its box here as on the stage).
  What the picture is drawn from changing in another way (the event's colours, font, frame or sample selfie) draws it again **by itself, after the editor's change** (next paragraph). **A welcome page that has a picture of its own keeps it** (that is the page's explicit choice): an event whose welcome page should follow its screen has none on the page.
- **Drawn again by itself when a source is changed (issue 327, `lib/screen/welcome-redraw.ts`; the plan's items 24 and 28: "always the latest generated").** The picture is drawn from the default slideshow's screen design, the event's colours and font, its frame and its sample selfie. A slideshow save and the buttons of the card already draw it; **the other sources now draw it again after the response of the save that changed them**: the event's brand colours or the colours of the Start button (`PATCH /api/events/<id>`, only when they really changed), a new generated frame (`generateFrameVariants`, so also an editor's frame messages and slots, the refresh from messmass, the partner's default slots), a new messmass style for the event (`refreshEventTheme`, only when the snapshot changed), the event's own sample selfies and its choice (`PUT` and upload of `.../selfie-slot`), and, at the partner level, the partner's default brand colours and its sample selfies (`PATCH /api/partners/<id>`, `.../selfie-slot`), which reach the partner's events.
  - **Nothing changes by itself.** Nothing runs on a timer, a visit or a deploy. A trigger only asks; the draw compares the key of everything the picture is drawn from with the stored one, so **an event whose sources did not change is read, not drawn**: no upload, no fetch (the overlay is fetched only when something is drawn), no write, and its stored picture, its key and its pages stay exactly as they were (tested on an event that has its own welcome page picture, like MTK x Vasas). **Only an event that has a stored picture is touched**: an event without one never gets one this way, because drawing it would also give it a default welcome page (that is the backfill, an admin's choice behind a dry run). The default slideshow is never made by it.
  - **Never blocks the save.** It is scheduled with `after()`, so the response is already sent; a failure is logged (`welcome_screen.redraw_failed`) and swallowed.
  - **Debounced and bounded.** The first change waits 2.5 seconds and then reads the event as it is stored then, so five changes in a row are one draw; a change that comes while the draw runs gets one more (at most two more); one draw at a time in a server instance, each cut off after 25 seconds; at most 40 events wait in one instance (`welcome_screen.redraw_dropped`); a partner-level change draws at most 25 events and stops after 40 seconds (`welcome_screen.redraw_capped`). The state is per server instance: two instances may both draw, and the second finds the same key (or overwrites the same file with the same bytes).
  - **A switch.** `WELCOME_SCREEN_AUTO_REDRAW=off` (also `0`, `false`, `no`) on the Vercel project turns all of it off at once (RUNBOOK, "The welcome page screen picture").
  - **What does not trigger it, and why.** *The global sample selfies* (a global admin switching one on or off or adding one): they reach every event, so the editor presses **Pick another** or **Draw it again** on the events that matter. *A deleted or switched-off partner or event upload*: the next trigger or the Draw button replaces the pick (a gone picture is never tried). *The tracked link and the written address*: the QR code's address and the text under the window are part of the default slideshow's screen design, so changing them is a slideshow save, which draws; the event's short address (`shortUrlSlug`) or the "Giant screen" link being switched off does not change the stored design, hence not the picture. *The bulk frame backfill* of lib/frame/backfill.ts goes through `generateFrameVariants`, so it does trigger (bounded as above).
- **Limits:** a text that is wider than its box is drawn like the stage draws it (not shrunk); the line is placed in the middle of a 1.15 line box, which is the stage's within a pixel or two, not identical.
- **Fixed 2026-10-09 (issue 520): the capture page never copied `Event.welcomeScreen` from the public event into its state** (`lib/events/welcome-screen-url.ts` does it now), so a welcome page without a picture of its own showed no giant screen at all; the line below described what was meant, not what happened, until then. It was found when the owner's MTK welcome page lost its static picture to follow the slideshow and showed an empty space.
- **Shown on the welcome page (step 8b):** the capture page's welcome step shows it on any welcome page with no picture of its own (`event.welcomeScreen.url`), and an event that gets the journey defaults, has the picture and has no welcome page of its own gets a default welcome page (docs/JOURNEY_DEFAULT_PAGES.md). An event without the picture is unchanged.
- **The photo window (issue 540, step 4 of `docs/WELCOME_SCREEN_PHOTO_PLAN.md`):** it shows the event's **sample selfie** with the event's frame over it, or the drawn stand-in. The sample selfie is one of what the event uses (`docs/LIBRARIES.md`, section Sample selfies: its own, its partner's, the global ones), **picked once and stored** on the event (`Event.welcomeWindow.pick`) so the picture does not change on every redraw; it is picked again when it is no longer among them, when its picture cannot be fetched (the next one is tried, never an error), or when the editor presses **Pick another**. A picture the registry knows is gone (`picture_health`) is never tried. **With no sample selfie in the system nothing changes: the stand-in is drawn and keeps its stored key.** The editor chooses on the event's Slideshows page, card **Welcome page screen**: **Sample selfie** (the default) with its panel (the same as the logo: use the default, choose, upload, add more, replace) and **Pick another**, or **Keep the stand-in** (`Event.welcomeWindow.source`); a choice draws the picture again in one press (`GET`, `PUT /api/admin/events/<id>/welcome-window`; `lib/screen/welcome-window.ts`). A portrait selfie is cropped to the wide window a little above the middle, so the head stays. **A photo of the event (step 5, owner answers 256 and 257):** the third choice, **A photo of this event**, with **Choose from the gallery** (`GET /api/admin/events/<id>/welcome-photos`: up to 60 photos, the editor's own gallery uploads first, then the newest approved photos; no name or e-mail of a guest; `PUT .../welcome-window` with `{ source: 'photo', photoId }`, `lib/screen/welcome-photo.ts`). **An editor's upload is clean** (its plain original when the frame was put on it, `originalImageUrl`) and is drawn like a sample selfie, **with the event's frame over it**; **any other photo is framed already** and is drawn as it is, **with no second frame** (the frame is not even fetched). **Only a photo that passes the one visibility rule can be chosen or shown** (approved, not hidden, not archived, not broken, not a try-on result, of this event) and **nothing else is asked** (answer 256: every approved or uploaded image may be used anywhere, any time, in any context). A chosen photo that can no longer be shown, or cannot be fetched, is replaced by a sample selfie and then by the stand-in: never an error. A photo is never a sample selfie pick. There is no gallery shortcut: the photo card of the gallery holds at most four buttons, so the choice is made on this card. Later steps: the latest approved photo (step 6) and the live stage's empty state (step 7), after the match.

## Existing events: the backfill (issue 326, issue 327; owner question 180)

Only a new event gets the default slideshow and the welcome page screen picture by itself. The events made before have neither (a read-only check of 2026-10-09 found 212 events, 2 of them with a welcome page of their own). The card **Welcome page screens for existing events** on the Slideshows page (global admins; `lib/screen/welcome-backfill.ts`, `GET` and `POST /api/admin/welcome-screen-backfill`, `components/admin/WelcomeScreenBackfillCard.tsx`) gives them to the events an admin chooses. **Nothing runs by itself and nothing is selected for you.**

- **The dry run** (**Count what would be made**, `GET`) reads the events, their default slideshows and the journey defaults switch, and **writes nothing**. It counts the events with no picture (and how many have no default slideshow, are upcoming from today, or are inactive) and lists them, upcoming ones first. For each it says **what its users would see differently** once it has the picture: **New first page** (the event gets the journey defaults and has no welcome page of its own: the default welcome page, the giant screen and the Start button, becomes its first page), **Picture on its welcome page** (it has a welcome page with no picture of its own: that page shows the drawn picture), or **No visible change** (its welcome page keeps its own picture, or the event does not get the defaults). With the journey defaults switch on (it has been since 2026-10-08) almost every existing event is **New first page**: that is the visible change the owner decides on, which is why the list shows it per event.
- **The run** (**Make for N events**, `POST { confirm: true, eventIds }`) works **only on the events it is given, never on "all"**: the card sends the ids of the events ticked in the list, after a confirmation in the page that says how many events will show their users something new. For each event, up to four per call and 40 seconds, it makes the default slideshow when the event has none (with its tracked "Giant screen" link and the stage picture) and draws the picture (`ensureWelcomeScreen`); the card calls again for the rest and can be stopped. A body without `confirm: true` or without ids is refused.
- **It only adds.** A tracked link, a slideshow, two pictures in Vercel Blob (`screens/<event uuid>/`), `Event.welcomeScreen`. Nothing is deleted, no page of the event is changed (a welcome page's own picture is never touched; tested), and an event that already has the picture is skipped, so a repeat is safe. A failure is reported for that event with its reason and the others go on; a failed event is still in the next count (a repeat only does what is missing).
- **Not run by this change.** The owner's recommendation (question 180) is: not before the match on 16 October; after it a dry run, then the events the owner names (or only the upcoming ones first).

## The stage on a stadium background (issue 326)

The card **Default stage** on the event's Slideshows page (`components/admin/DefaultStageCard.tsx`, `GET` and `PUT /api/admin/events/<id>/stage-background`, `lib/screen/stage-redraw.ts`) shows the stage of the default slideshow, the stadium background it is drawn on (the stored pick) and how many the event can use, and holds the panel **Stadium backgrounds** (use the default, choose, upload, add more, replace, none: the same panel as the logo and the sample selfie).

- **Draw the stage again** draws the stage on what the event uses now: the stored pick while it is still among them, else a random one, else the stage drawn by code. **Pick another** takes another one. Choosing in the panel does the same in one press. The picture is stored at `screens/<event uuid>/default-<hash>.png` (the same stage gives the same address, so asking again with nothing changed writes nothing), the default slideshow's `screenDesign.overlayImageUrl` is pointed at it and `reloadRequestedAt` is set, so the open screens reload like after any save of the slideshow; when the event has the welcome page screen picture and the stage changed, that picture is drawn again after it (an event without it is not given one).
- **Only a stage the system drew is drawn again.** A slideshow whose overlay is a picture an editor chose (`isGeneratedOverlay`: the address is not `screens/<event uuid>/default-...`; the designers' picture of MTK x Vasas is one) is never touched; the route answers 409 and the card says so.
- **Back to the stage drawn by code:** choose **Show nothing here** in the panel (the slot's None) or switch the stadium backgrounds off in the library, then Draw the stage again: the stage returns to the very picture, at the very address, it had before the library existed, and the stored pick is removed.

## Limits

- 16:9 only: the design is positioned for the designers' 1920×1080 stage; another stage aspect shifts it.
- The QR code points to the address given. Counting scans per placement (a short link for each place the QR is shown) is a separate step.
- The text stays on one line and is not shrunk to fit: shorten it if it is too long for its box.
