# Default pages of the user flow and the global switch

Planned with the owner on 2026-10-07 (`docs/WELCOME_AND_DEFAULTS_PLAN.md`, items 26, 34 to 48); delivered by camera#330. Main rule: every element is generated into a ready-to-go default and the editor can always replace it; what an event has set is never deleted.

## The default order

Welcome page, **consent page**, **login page** ("Who are you?"), selfie taking, the rest. The two defaults are added **at read time** (`GET /api/events/[eventId]?audience=guest`, `lib/events/default-pages.ts` and `lib/events/identity-page.ts`), never stored in the event's own pages:

- **Consent page** (`DEFAULT_CONSENT_PAGE_ID`): added right after the leading welcome page(s) when the event gets the journey defaults and has no consent page ("accept" page) before the photo. Three required checkboxes, each with a link that opens in a new tab: "I accept the Terms and conditions" (`https://seyuselfies.com/en/legal/terms`), "I accept cookies" (`https://seyuselfies.com/en/legal/cookies`), "I have read the Privacy policy" (`https://seyuselfies.com/en/policies`). English by default; another language is typed per event. No consent text is drafted: the wording is the legal pages.
- **Login page**: unchanged in content; added for an event that requires vetting (all events now) when it has no login page before the photo. It now sits after the consent page: an event's own consent page right after the welcome page keeps the login behind it.
- **An event's own pages win**: an own consent or login page before the photo is kept and no default of that kind is added.

## The journey view in the page editor (camera#378, items 134 to 137)

The list in the event editor ("Pages of the user journey", `components/admin/CustomPagesManager.tsx`) is the journey **as the user goes through it**, built by `effectiveJourney` (`lib/events/journey.ts`) from the stored pages with the **same function the user's page uses** (`withDefaultJourneyPages`), so the editor and the user cannot disagree (a test compares them). What decides which defaults the event gets (`vettingRequired`, `consentDefault`, `language`) comes from `GET /api/events/<id>` as `journeyContext`.

- **Own pages** are listed as before (move, edit, delete); a page that is switched off stays in the list, marked "Switched off", because the editor must be able to reach it.
- **Default pages** (the welcome, consent and login page) are rows marked **Default**, with a sentence saying why they are there. They cannot be deleted. **They have the up and down buttons like every page** (issue 535, owner 2026-10-10: "there should be an up/down for the Accept/Who-are-you section as well"): a default page stays a default (its texts still follow the Dictionary and the text levels) and only its **place** is the event's choice, saved as `Event.defaultPageOrders` (`{ 'default-consent': 2, ... }`, only the three known ids and finite numbers, `sanitizeDefaultPageOrders`) by **Save Pages**. Without saved places they are in their default places (welcome first, then consent, then login). **A default page never swaps with the take-photo page** (`moveTarget`, `lib/events/journey.ts`): the consent and the login come before the photo, because a photo that is checked needs an identity first (camera#264); an own page moves anywhere. One move numbers **every page row together** (own pages as their `order`, default pages as their saved place; `moveJourneyRow`, `renumberJourney`), so the editor and the user keep one order; the built-in steps are not pages and stay where they are. The user gets the same places because `withDefaultJourneyPages` takes `defaultOrders` from the same event field in the event API and in the journey the editor builds.
- **Customise** opens the editor on a **new own page filled with the default's texts, in the default's place**; it is stored only when the editor saves the page and then "Save Pages". The own page wins, so the user's journey does not change by it. **Deleting the own page brings the default back.**
- **Built-in steps** are rows marked **Built in**, after the take-photo page: the waiting screen (with approval) or the share screen (without), the e-mails and the public photo page. They are not pages; each says where its texts are edited.
- **Default welcome page (issue 327, step 8b):** a **welcome page** row marked Default is added first, but **only** for an event that gets the journey defaults, **has the picture drawn from its default slideshow** (`Event.welcomeScreen`, docs/SCREEN_DESIGN.md) and has **no welcome page of its own** (a switched off welcome page counts as its own: the editor chose). Its texts come from the dictionary (`welcome.title`, `welcome.button`, English and Hungarian). It carries **no picture of its own**: the capture page shows the picture drawn from the default slideshow on **every welcome page that has none**, so the page follows the default slideshow, an own picture on a page always wins, and Customise copies no picture into the own page. An event without the picture (every existing event today) gets no default welcome page and its pages are exactly what they were.

## Take photo + Submit: pages between taking the photo and saving it (issue 535, step 2; owner 2026-10-10)

Owner: "there is a common flow to take an image and then login to be able to submit ... I need a checkbox in the Take Photo page to show it there as it is now built in or uncheck and able to add steps between them, like the CTA or the who are you."

- **The pair.** Taking the photo and submitting it are a pair, like the consent and the login. **Ticked (the default, as it always was): Submit is part of the Take Photo page**: Continue on the reframe screen saves the photo. **Unticked** (the checkbox **Submit is part of this page** in the Take Photo page editor; it takes effect at once in the list and is saved with Save Pages): a **Submit** row (a marker page, `pageType: 'submit'`, `[Submit]`, no texts of its own) is put right after the Take Photo page, and **the pages between the two run after the photo is taken and before it is saved**: a Who are you page (login), a CTA page, an Accept page. The pages after the Submit page run after the save, as the pages after the Take Photo page always did. The built-in steps (waiting or share screen, e-mails, public photo page) follow the Submit row. Ticking the box again takes the marker out.
- **Where the code is.** `splitCustomPages` (`lib/capture/split-pages.ts`) splits the pages into before the photo, **between the photo and the save** (`presubmitPages`), and after; the capture page's `flowPhase` has the new phase `presubmit`: Continue on the reframe screen makes the picture and, when there are such pages, shows them instead of saving; the last one calls `finishPresubmit`, which sets `saveRequested`, and the capture screen saves. A failed save does not ask for the pages again (`presubmitDone`), and neither does the next photo of the same user; a restart does. `pagesBeforeSave` (`lib/events/photo-boundary.ts`) says what counts as before the save for the defaults (a login or consent page between the two counts, so no default login is added a second time) and for the acceptance on the login page. The editor: `setSubmitSeparate`, `hasSeparateSubmit` (`lib/events/journey.ts`); `moveTarget` keeps the Submit row after the Take Photo page, and **with a Submit row a default page may move between the two but never behind the Submit row**.
- **Social sign-in is not offered between the photo and the save.** A sign-in with Google or Facebook leaves the page and the photo lives in the page's memory only, so it would be lost; a Who are you page in that place shows the name and e-mail form only (the page's social switch is ignored there). Keeping the photo across a social sign-in is a separate, larger step (the picture and the frame choices would have to be stored and restored); it is on issue 535 as a question for the owner.
- **Nothing changes for an event whose editor does not untick the box**: no Submit page, no new phase.
- **Verified** in a browser against a production build with the API mocked at the network level (nothing is written anywhere): a login between the photo and the Submit page (nothing saved before it, no social buttons, the contact is saved with the photo), no Submit page (saves at once), a CTA between, a Submit page with nothing before it, and a failed save after the login (Continue saves again without asking for the login).

## The consent page

The `accept` page type takes a **list of checkboxes** (`config.checkboxes`: a text and an optional https link each, up to ten), all required: Continue works only when every one is ticked. A page that only has the older single `checkboxText` shows one checkbox, exactly as before. The finished page leaves **one consent record per checkbox** in the submission's `consents` list (the exact text, the link, the time; `UserConsent.linkUrl` is new and optional). The server does not refuse a photo without a recorded consent (owner decision, item 43): the page itself blocks the user. The admin pages editor edits the list (add, remove, text, link); saving drops a link that is not https and any checkbox without a text.

## The public gallery permission (issue 554, owner answer 283)

Some services and markets need the user's own permission before a photo is shown on a public wall or gallery (the pledge wall, savetheworld's galleries); for others the terms the user accepts are enough, as they always were. So it is a **setting**, not a rule: the **partner** has a default (Partner editor, section *Public gallery permission*: **Do not ask** (standard) or **Ask**), an **event** follows it or chooses for itself (the consent page settings: the select *Permission to show the photo in the public gallery* at the top of the journey editor and inside the consent page's editor, the same value, saved with **Save all**: Same as the partner / Ask / Do not ask). Nothing is copied down, and **no event asks until somebody chooses**.

When an event asks, the photo page shows **one optional checkbox, not ticked,** on the step where the photo is saved (under the reframe, above **Continue**; the words are the Dictionary texts `share.publicGalleryConsent` and `share.publicGalleryConsentHelp`, English and Hungarian, editable at every text level; the default sentence says the photo goes on the **public campaign wall**, because that is what the flag controls: savetheworld's public pledge wall and galleries, not the giant screen at the venue, the person's own share link or the e-mails, which follow the approval rule only; owner answer 289). Only a **ticked** box makes the photo eligible for the wall (`shareOptIn`), and it is kept as evidence: `Submission.publicGalleryConsent = { version: 1, grantedAt }` (the version is that of the sentence). The box is for **one photo** (a retake or the next photo starts unticked). **The server decides from the event's own setting** (`lib/events/gallery-consent.ts`): when the event asks, a request without the ticked box and the version is a private photo, so an old page that does not know the setting cannot put it on the wall; when the event does not ask, `shareOptIn` is what the page sends, as before. A vetted event keeps the choice for the approval (`photoReview.shareOptIn`). Photos taken before the setting are untouched. The legal wording is validated by whoever can edit it (answer 251), not by the code.

## Checkbox settings: every checkbox is shown or not, and required or optional (issue 558, owner answer 297)

Owner, 2026-10-10: "all types of checkboxes have to have an on/off toggle and a required checkbox on the settings as every market has its own law." So every checkbox a user can meet has **two settings, shown or not and required or optional**, chosen where the brick model puts every choice: the **partner** has a default, an **event** follows it ("Same as the partner") or chooses for itself, nothing is copied down (`lib/events/checkbox-settings.ts`, `effectiveCheckboxes`). **The standard of every kind is what the journey did before, so no event changes until somebody chooses** (proved by `lib/events/consent-settings.baseline.test.ts`, which runs the same inputs through the frozen old logic in `lib/events/baseline/` and the new, and `components/capture/consent-defaults.test.tsx`, which holds the markup of the guest pages to the markup they had).

### Every kind of checkbox, and what the two settings mean for it

| Kind | The checkbox the user meets | Standard (today) | Off | Optional | Required |
|---|---|---|---|---|---|
| `terms`, `cookies`, `privacy` | the three documents of the **default consent page** ("I accept the Terms and conditions", "I accept cookies", "I have read the Privacy policy") | shown, required | not shown, no record; all three off: no default consent page | shown with "(optional)", may stay unticked; a record either way | Continue waits for the tick; the server checks it too |
| a checkbox of an **own consent page** | each checkbox in the page editor (`config.checkboxes[]`) | shown, required | `shown: false`: not shown, no record; a page with all of them off is not a step | `required: false`: as above | `required: true`: Continue waits; the server checks it too |
| `acceptance` | the one sentence on the **Who-are-you page** that stands for the consent page's checkboxes (issue 523) | off (the consent page is a page of its own) | the consent page is a page of its own | on the page, nothing waits for it; the records say whether it was ticked | on the page, everything is off until it is ticked; the server checks it too |
| `gallery` | permission to show the photo on the public campaign wall (issue 554), on the photo step above Continue | off (does not ask) | not asked, the terms cover it | asks, a box not ticked, may stay unticked (this was "Ask") | Continue on the photo step waits for the tick; the server refuses a save without it |
| CTA page | no checkbox: the CTA record is the visit of the link | n/a | n/a | n/a | n/a |
| profile consent "C" (docs/PROFILE_PURPOSE_AND_CONSENT_DRAFT.md) | not built yet: its own unticked, optional checkbox | not shown | | | joins this table when it is built, with the same two settings |

### Where a setting is stored
- The two kinds that had a setting keep it where it was, so nothing is migrated: `galleryConsent` (true asks, false does not, null follows the partner) is the "shown" of the gallery permission and `acceptanceOnWhoAreYou` (now also null) the "shown" of the acceptance sentence. Everything else is in `consentSettings` on the **partner** and on the **event**: `{ terms | cookies | privacy: { shown?, required? }, acceptance: { required? }, gallery: { required? } }` (`PATCH /api/partners/<id>` and `PATCH /api/events/<id>`; unknown kinds or parts are refused).
- The **first level that made a choice for a kind decides both of its settings**: event, else partner, else the standard. A part the deciding level did not set takes the standard, never the partner's (an event that chose "ask" does not become "required" because its partner did). The checkboxes of an event's **own** consent page carry their own two settings (`shown`, `required` on each item); an own page wins over the defaults, as every own page does.
- The default consent page (`withDefaultJourneyPages`, `defaultConsentCheckboxes(language, texts, documents)`) is built at read time from the effective settings of the three documents. `GET /api/events/<id>?audience=guest` sends a guest only the checkboxes that are on (`withShownCheckboxes`), `acceptanceOnWhoAreYou` as the effective value, and `effectiveGalleryConsent`, `effectiveGalleryRequired`, `effectiveAcceptanceRequired`. The editor view of the same route (not a guest) adds `effectiveCheckboxes` (what the event gets, with the level that decided) and `partnerCheckboxes` (what it would get if it followed its partner), so "Same as the partner" can say what it gives.

### What the server checks (the page is never the only guard)
- **A requirement an editor chose** (`required: true` stored at the event or the partner, on a checkbox of an own page, or the gallery permission set to required) is checked by the server (`lib/events/consent-guard.ts`, called first in `POST /api/submissions`, before anything is uploaded): the journey the user got is rebuilt with the same functions the user's page uses, and the request must carry as many **accepted** consent records for each consent page before the save as the page has required checkboxes (for the acceptance sentence: one per shown checkbox, since one tick records them all). The count is compared, not the text, so a word corrected while a user is on the page does not stop their save. A missing consent answers 400 "A required consent is missing"; a missing gallery permission 400 "The permission to show the photo in the public gallery is required" (both translated for the page, `err.consentRequired`, `err.galleryRequired`).
- **The standard requirement stays with the page**, exactly as before (planning item 43: the server never refused a photo without a recorded consent), so a live event changes only when somebody chooses. `ENFORCE_STANDARD_REQUIREMENTS` in `lib/events/consent-guard.ts` is the one switch that would make the server refuse those too; it is off until the owner decides (after the match of 2026-10-16).
- An event that chose nothing costs the server nothing extra beyond reading its partner: the rollout switch is read only when a requirement was chosen.

### What the records keep
Every consent record is still one per checkbox (exact text, link, time, and the one sentence for the acceptance on Who-are-you). New: an **optional** checkbox carries `required: false`, and one that was shown and **left unticked** leaves a record with `accepted: false` (the time is when the user answered), so what was shown and what was ticked are both kept; the server accepts `accepted: false` only on a record that says `required: false`. A checkbox that is **off** leaves nothing. The gallery permission keeps its evidence (`publicGalleryConsent = { version: 1, grantedAt }`, the version is that of the sentence), now with `required: true` when the event required it; an optional box left unticked leaves no evidence, as before (the missing evidence together with `isShareVisible: false` is the answer). Every wording is a Dictionary text, editable at the global, partner and event levels: the three documents (`consent.*`), the optional marker (`accept.optional`), the gallery sentence (`share.publicGalleryConsent`, `share.publicGalleryConsentHelp`, and for the required variant `share.publicGalleryConsentRequired`, `share.publicGalleryConsentHelpRequired`).

## The login page rules

Social login and the email form are each optional, but **at least one stays on**: with both switched off the default (both on) applies (`loginOptions`). An empty heading, text, label or button text falls back to its default text (`DEFAULT_IDENTITY_TEXTS`).

## The global switch (item 26)

`Event.journeyDefaults` is set on every event created from now on (camera admin and provisioning from messmass), and such an event gets the defaults. **Existing events get them only when the switch is on**: Admin, Settings, **Journey defaults** (`/admin/settings/defaults`, `GET/PATCH /api/admin/settings/defaults-rollout`, global admins, stored in `admin_settings` as `defaults-rollout`; off until an admin turns it on). Turning it on shows the default consent page at once on every existing event that has no consent page of its own, including events that are running; turning it off takes them away again. Nothing in an event's own pages is ever changed.

**State:** the switch was turned **on** on 2026-10-08 at 06:10 UTC, on the owner's instruction (a script upserted `applyToExistingEvents: true`; the previous state was no setting). Live check right after: the real MTK Budapest x Vasas event shows welcome, the default consent page, then the login page; events that have their own consent page (for example FIBA 3X3 2026 TRYON) keep it and get no second one. To take the defaults away again set the switch off on the Journey defaults page.

The rest of the planned defaults (the default slideshow and the global defaults library, the welcome page screen, the share page, the editable texts) are separate packages, see the plan.

## The acceptance on the Who-are-you page (issue 523; client feedback 2026-10-09)

An event can show its consent page's checkboxes as **one small checkbox with one sentence on the Who-are-you page**, under the intro text and above the sign-in buttons, instead of a page of its own: "Elfogadom az Általános Szerződési Feltételeket, tudomásul veszem az Adatkezelési tájékoztatót és a Sütikezelési tájékoztatót" (English: "I accept the Terms and conditions, and I acknowledge the Privacy notice and the Cookie notice"). **Everything on the page is off until the box is ticked**: the Google and Facebook buttons (they have no address while off), the name and e-mail fields and the continue button.

- **One setting, two editors:** `Event.acceptanceOnWhoAreYou` (off unless an editor turns it on; `PATCH /api/events/<id>` takes a true or false). The Who-are-you page editor shows it as **Show acceptance** and the consent page editor as **Show it on Who-are-you**; both read and write the same value in the pages manager and it is saved with **Save all**. A default page (not yet customised) has no editor: use **Customise** first. Off: the two pages one after the other, as before.
- **When it applies (`acceptanceOnLogin`, `lib/events/acceptance.ts`):** the switch is on, and the event has an active Who-are-you page and an active consent page, both before the photo. The first such consent page leaves the list of steps; if one of the two pages is missing or switched off, or the consent page comes after the photo, nothing changes and the user still gets a consent page. A second consent page stays a page of its own.
- **The sentence (`acceptanceSentence`):** the usual three legal pages (the terms, the cookies, the privacy policy, in that order, as `defaultConsentCheckboxes`) make the dictionary sentence `consent.combined` with its three link texts (`consent.combined.terms`, `.privacy`, `.cookies`); each name is a link to its page, opening in a new tab. The wording can be written per language, event or partner in the Texts editors like every other text. Any other list of checkboxes on the consent page is shown as its own texts one after the other with their links, so nothing the user is asked to accept is left out.
- **The record:** ticking the box leaves **the same consent records** as the separate page, one per document (its exact text, its link, the time), and each now carries `shownText`, the one sentence the user read. They are made **when the box is ticked** (not when the page is left) because a sign-in leaves the page.
- **A sign-in no longer loses what was accepted (`lib/capture/consent-memory.ts`):** signing in with Google or Facebook leaves the page and comes back to it, and the page's own state went with it, so the acceptances given before the sign-in were lost and the photo of a user who signed in was saved without consents (this was true for the separate consent page too). The acceptances are now kept in `sessionStorage` for 30 minutes, read back only when the page is resumed after a sign-in, and removed when the flow starts over.
- **Consent law (to settle with whoever advises on it):** one tick for the terms and for taking note of the two notices matches the client's sentence ("accept" for the terms, "take note" for the privacy and cookie notices). Anything beyond essential cookies (analytics, profiling: issue 521) would need its own separate, optional consent, not this tick.
